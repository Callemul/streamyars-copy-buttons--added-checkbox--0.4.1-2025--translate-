# C4.4 — post-T20 module consolidation assessment

Date: 2026-09-11. Inspected checkout: `b826edd`, including the current working-tree documentation. Status: assessment only; no implementation or commit.

## Recommendation

Keep the T20 domain layout. Three optional, bounded consolidations below can remove redundant navigation while preserving existing public import paths. None is a correctness fix or a prerequisite for shipping. Prefer the messaging pair first; defer the others if the small navigation benefit does not justify touching working code.

Small modules are valid. A single production consumer is a reason to inspect cohesion, not a reason to merge. Directory imports resolving to `index.ts` are also valid. This assessment uses responsibility, actual consumers, runtime dependency direction, state ownership, and test seams; it imposes no line-count threshold or target module count.

## Evidence and scope

- Read `AGENTS.md`, `RTK.md`, `docs/plans/T20-modules-layout.md`, the current architecture, the project StreamYard skill, and testing rules. T20 is historical design evidence; its old file paths and counts were not treated as current facts.
- An in-memory TypeScript AST scan examined 405 source/test files across `modules/`, `youtube/`, `popup/`, `options/`, `background/`, `tests/`, and `main.ts`. At scan time, `modules/` contained 169 `.ts` files. T20's original 170 included `render_utils.ts`, now in `popup/`.
- Inspected import declarations, re-exports, and literal dynamic import/require calls, resolving relative paths as files or directory indexes. All relative specifiers encountered by this scan resolved. This is a static import check, not proof of runtime behavior; computed paths and non-import string references require separate searching before implementation.
- Distinguished explicit type-only edges from value edges. A separate value-edge graph check over `modules/` found no file or directory cycles. An in-memory contraction of all three proposed pairs also found none. This checks dependency topology, not module evaluation equivalence or a compiled bundle.
- Read the candidate implementations and searched their consumers and tests. “Consumer” below means a direct importing/re-exporting production file, with tests listed separately. Public re-exports are followed when assessing the actual audience; they do not make their implementation leaves unused.
- `tsconfig.json` uses `moduleResolution: "bundler"`; `tests/ts_loader.js` explicitly resolves both `.ts` files and `/index.ts`. Existing directory-index entry points are intentional and need no repair.

These candidates qualify because of overlapping ownership and consumers, not because either file is short. C1 and C3 consolidate an entry with its sole assembly implementation; they do **not** flatten the service or UI subsystem. Keeping either pair is also defensible if a stable entry/implementation distinction is preferred.

## Keep the reviewed boundaries

| Modules / group | Consumer evidence and reason to keep |
|---|---|
| `core/fuzzy_window.ts` and `core/fuzzy_match.ts` | Window geometry is consumed by the matcher, but accepts the distance function as an argument and has direct tests in `tests/fuzzy_match.test.js`. It isolates traversal and error-budget rules from the distance metric. One consumer does not erase that useful algorithm boundary. |
| `comments/assistant/trigger_{words,regex,category}.ts` | Each feeds `trigger_manager.ts`, but word configuration, cached regex construction/reset, and category precedence are different responsibilities. In particular, the regex cache owns mutable `lastIndex` handling; merging it into the manager would hide that contract. Keep the manager's delegation. |
| `stats/stats_session.ts` | Used by `stats_auto_phase.ts`, `stats_live_sampler.ts`, `stats_phase_marker.ts`, and `stats_tracker.ts`; directly tested in `tests/stats_session.test.js`. Keeps session operations independent of timers and DOM. The brand lookup helper could be revisited if that domain grows, but moving it now has no demonstrated payoff. |
| `streamyard/ui/ui_shared_utils.ts` and its leaves | The shared facade exposes DOM updates, scroll behavior, checkbox restoration, and filter-control binding to multiple UI consumers. A leaf whose only direct importer is the facade still serves those consumers. Keep separate responsibilities; do not recreate the former miscellaneous utility implementation. |
| `video/video_copier_ui.ts` and injection modules | The entry imports four distinct injection surfaces and owns `VIDEO_COPIER_INJECTIONS`. Title, share-modal, card, and master-download controls have different DOM contracts. The facade is actual composition and the leaves are surface boundaries; one direct facade consumer each is expected. |
| `streamyard/banners/deletion*.ts` | `deletion.ts` exposes calculations, execution, and the action handler to `index.ts` and `mouseup_handler.ts`; the handler imports calculations and execution directly. Keep counting/message construction, confirmation orchestration, and destructive DOM clicks distinct. Calculations also read DOM, so this is not described as a wholly pure-vs-DOM split. The short execution module remains a useful effect boundary. |
| `streamyard/comments/action_{effects,marking,dom_sync}.ts` | `action_effects.ts` is shared by `comments/index.ts` and the adapter; it delegates marking and DOM synchronization. Keep effect orchestration and state synchronization separate rather than placing service/state manipulation in one-off handlers. |
| `banners/banner_executor.ts` and `banner_form.ts` | Both feed `banner_creator.ts`, but execution owns ordered asynchronous creation, pauses, category persistence, and per-item error cleanup, while form helpers own DOM interaction. These are meaningful workflow seams despite their single caller. |
| `storage/storage_runtime.ts`, async/callback operations, keys, migration | Runtime plumbing has a distinct context/listener contract and preserves dynamic adapter dispatch. Keep the storage service and its implementation boundaries. Do not combine schema, migration, or persistence behavior merely to reduce files. T20's suggested optional schema extraction addresses type organization and is not a required C4.4 consolidation or runtime-cycle fix. |
| `comments/comment_service.ts` and stores | The collected, checkbox-state, and prayer-record stores are each reached through the service. This is deliberate service ownership, not redundant indirection to remove. Keep UI and platform consumers routed through the service. |
| Existing `index.ts`, registry, DOM primitive, and type modules | Directory indexes can be real entry points or useful aggregators. Registry records remain SSOT, and type-only reverse references are allowed. No broad flattening, new barrels, cross-domain moves, or small-file cleanup is justified by this assessment. |

## Implementation gates for a later task

1. Re-scan the current imports and string references before removing any file; the checkout may change after this assessment. Include tests, mocks, and documentation references. The current scan found no direct test consumer of the three removal paths.
2. Apply one candidate at a time, keeping exports and behavior unchanged. Do not combine this with selectors, parsing fixes, data migrations, action semantics, or lifecycle changes. Read the applicable technical rules before implementation.
3. Recheck value-edge cycles at file and domain-directory levels, with type-only imports excluded. All proposed destinations stay within their existing domain directories. Do not “fix” directory-index imports or count type-only back references as runtime cycles.
4. Run the existing behavior tests named above using the project's strip-types loader and happy-dom setup. Add tests only if a real behavioral gap is found; import relocation alone does not justify new implementation-mirroring tests.
5. Run `npm run verify` after implementation (through RTK where available). Review the diff for preserved public entry paths, singleton identity, state delegation, and absence of unrelated edits. No commit is authorized by this assessment.
