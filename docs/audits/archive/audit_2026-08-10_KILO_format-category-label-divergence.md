## 1. Що саме зламано (з порівнянням реального контракту і того, як його викликали, а також помилками tsc, якщо вони є)

Існує **дві незалежні реалізації** `formatCategoryLabel`:

1. `youtube/studio/studio_header_counters.ts` → `formatCategoryLabel(authorName, category)`.
2. `youtube/studio/studio_ui.ts` → **локальна копія** `formatCategoryLabel(authorName, category)`.

Обидві роблять одне й те саме призначення — зібрати підпис категорії для баджа/картки, — але
**мають різний пріоритет і різне підсвічування** `<b>`.

Контракт у `studio_header_counters.ts` (канонічний, зафіксований тестом
`tests/studio_header_counters.test.js` #6):

```ts
// youtube/studio/studio_header_counters.ts — НЕ ЗМІНЕНО в цій сесії
export function formatCategoryLabel(
  authorName: string,
  category: string | null | undefined,
): string {
  const cleanCategory = (category ?? '').trim();
  if (!cleanCategory) return escapeHtml(authorName);
  // нормалізація "проповіді" -> "проповеди" (українське -> російське)
  const normalized = cleanCategory.replace(/\bпроповіді\b/iu, 'проповеди');
  return `${escapeHtml(authorName)} <b>${escapeHtml(normalized)}</b>`;
}
```

Контракт у `studio_ui.ts` (локальна копія, ДУБЛЮЄ логіку, але з іншим пріоритетом):

```ts
// youtube/studio/studio_ui.ts — НЕ ЗМІНЕНО в цій сесії (локальна копія)
function formatCategoryLabel(authorName, category) {
  const cleanCategory = (category ?? '').trim();
  if (!cleanCategory) return escapeHtml(authorName);
  // ТУТ інший порядок/підсвічування: спочатку категорія, потім автор,
  // і <b> на іншому токені.
  return `<b>${escapeHtml(cleanCategory)}</b> ${escapeHtml(authorName)}`;
}
```

Помилок `tsc` немає — `studio_ui.ts` має власну (не експортовану) копію, тож типи не
конфліктують. Але це **порушення Single Source of Truth**: дві функції з однаковою назвою і
різним результатом.

Порівняння контрактів (на прикладі `authorName='Опарин/Молчанов'`, `category='проповеди'`):

| Реалізація | Результат | Відмінність |
|---|---|---|
| `studio_header_counters.formatCategoryLabel` | `Опарин/Молчанов <b>проповеди</b>` | автор + `<b>`категорія |
| `studio_ui.formatCategoryLabel` (локальна) | `<b>проповеди</b> Опарин/Молчанов` | `<b>`категорія + автор |

**Висновок:** порядок токенів і місце `<b>` — різні. Користувач бачить різне форматування
підпису залежно від того, який модуль малює бадж/картку.

## 2. Runtime-наслідки (детальний аналіз та трасування помилки)

### 2.1 Видимий для користувача розбіжний UX

- Баджі у шапці Studio (малює `studio_header_counters.ts` → `studio_header_dom.ts`) показують
  `<автор> <b><категорія></b>`.
- Картки/список у `studio_ui.ts` показують `<b><категорія></b> <автор>`.

Обидва живуть на одній сторінці Studio → користувач бачить **два різні стилі** для одного й
того ж поняття «категорія автора». Це не краш, але це плутанина і — головне — ознака того,
що логікуFormatter'а продубльовано.

### 2.2 Трасування

- `studio_header_counters.ts`: `formatCategoryLabel` експортується і використовується у
  `buildSheetBadgeHtml`/`buildCountersHtml` (тепер у `studio_header_badge_markup.ts`).
- `studio_ui.ts`: локальна `formatCategoryLabel` — приватна функція всередині модуля; не
  імпортує канонічну. Джерело дубля.

### 2.3 Чому це не впливає на існуючі тести

Характеристичний тест `tests/studio_header_counters.test.js` (#6) навмисно фіксує поведінку
канонічної функції (включно з нормалізацією «проповіді»→«проповеди»). Тест для `studio_ui.ts`
фіксує його власну копію. Зміна однієї з версій на користь іншої потребуватиме синхронізації
обох наборів тестів — тому виправлення виноситься в окремий аудит.

## 3. Пропоноване виправлення (приклад коду, який НЕ був застосований)

Єдине джерело істини — зробити `studio_ui.ts` споживачем канонічної функції:

```ts
// youtube/studio/studio_ui.ts — НЕ ЗАСТОСОВАНО
- import { ... } from './studio_header_counters';
- // видалити локальну formatCategoryLabel
+ import { formatCategoryLabel } from './studio_header_counters';
// далі використовувати імпортовану formatCategoryLabel(authorName, category)
```

Альтернатива (якщо два різні стилі — це *свідоме* рішення дизайну): тоді функції слід
перейменувати, щоб назва відображала відмінність (напр. `formatCategoryLabelHeader` /
`formatCategoryLabelCard`), і додати коментар-обґрунтування. **Але** поточний код не містить
жодного пояснення — тому за замовчуванням це сприймається як ненавмисний дубль.

### 3.1 Що зміниться для користувача (таблиця сценаріїв "Зараз" та "Після")

| # | Сценарій | Зараз | Після (варіант уніфікації) |
|---|----------|-------|----------------------------|
| 1 | Бадж у шапці Studio | `<автор> <b>категорія</b>` | без змін |
| 2 | Картка у `studio_ui` | `<b>категорія</b> <автор>` | `<автор> <b>категорія</b>` (узгоджено з баджем) |
| 3 | Пошук «проповіді» | `studio_ui` лишає як є; `header` нормалізує в «проповеди» | обидва нормалізують однаково |

> Для користувача зміна — узгоджене форматування підпису в усьому UI Studio.

### 3.2 Ризики міграції

1. **Ризик середній.** Якщо `studio_ui` свідомо мав інший стиль, уніфікація «під header»
   змінить вигляд карток. Потрібне підтвердження дизайну.
2. **Безпека екранування:** обидві версії використовують `escapeHtml`; уніфікація не втрачає
   екранування.
3. **Нормалізація «проповіді»→«проповеди»:** лише у `header`-версії. Якщо її перенести в
   `studio_ui`, поведінка карток зміниться (тести `studio_ui` доведеться оновити).
