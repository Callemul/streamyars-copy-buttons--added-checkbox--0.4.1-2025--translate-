## 2. Сильні сторони

1. **Модульність доведена до кінця.** Найбільший файл коду — 270 рядків (`youtube/studio/studio_adapter.ts`); медіана значно нижча. God-класів не лишилось.
2. **MV3-коректність service worker.** Усі слухачі (`onInstalled`, `onMessage`, `storage.onChanged`) підписані **синхронно** на верхньому рівні модуля — воркер коректно прокидається на події. Класична помилка MV3 (реєстрація слухача всередині `await`) відсутня.
3. **Нема `eval` / `new Function` / `document.write` / `executeScript`.** Динамічного виконання коду в кодовій базі немає взагалі.
4. **Текст коментарів екранується.** `TriggerHighlighter.escapeHTML` застосовується до тексту **до** вставки розмітки — сирий HTML з коментаря глядача (`<img src=x onerror=…>`) не виконується. Перевірено запуском реального модуля.
5. **Паритет локалей.** `en` / `uk` / `ru` — рівно по 13 ключів, розбіжностей немає.
6. **Спостерігачі прибираються.** 4 `new MutationObserver` проти 8 викликів `.disconnect()` — витоку спостерігачів не видно.

## 3. Знахідки

### 🟠 Середня важливість

#### C1. Каскадне заміщення в підсвітці руйнує розмітку коментаря
**Файл:** `modules/comment_assistant/highlighter.ts:32-52` → споживач `modules/comment_assistant/processor.ts:37` (`innerHTML =`)

`highlightTriggers` проганяє `String.replace` по рядку **послідовно для кожного тригерного слова**, дописуючи в той самий рядок розмітку `<mark class="syh-trigger-highlight syh-trigger-prayer" data-syh-trigger="…">`. Наступні ітерації бачать уже вставлену розмітку як звичайний текст і підсвічують **усередині тегів і атрибутів**.

Відтворено запуском реального модуля (тригерні слова `молитва` + `mark`, текст `прошу молитва`):

```
прошу <<mark class="…" data-syh-trigger="mark">mark</mark> class="…" data-syh-trigger="молитва">молитва</<mark …>mark</mark>>
```

Те саме з тригером `prayer` — розрив усередині значення `class`. Результат іде прямо в `innerHTML`, тож стример бачить понівечений коментар.

**Умова спрацювання:** у списку тригерів є латинське слово, що збігається з токеном згенерованої розмітки — `mark`, `prayer`, `question`, `highlight`, `class`, `data`, `syh`, `trigger`. Дефолтні списки кириличні, тому баг латентний, але «question»/«prayer» — цілком реалістичні тригери для англомовного ефіру.

**XSS?** Ні. Текст користувача екранований, а `data-syh-trigger` проганяється через `escapeHTML`, тож пролізти в обробник події не вийде. Це дефект коректності рендера, не вразливість.

**Напрямок фіксу:** один прохід — зібрати всі збіги, відсортувати за позицією, відкинути перекриття та зібрати рядок за одну ітерацію (або перейти на `Range`/`TreeWalker` по текстових вузлах замість рядкових замін).

---

#### C2. `lib/` у `.gitignore`, але `lib/chart.js` оголошений у `manifest.json`
**Файли:** `.gitignore:2`, `manifest.json:41`

`manifest.json` декларує `lib/chart.js` у `web_accessible_resources`, а `.gitignore` виключає всю теку `lib/` (підтверджено: `git ls-files lib/` порожній). Свіжий клон репозиторію **не містить** `lib/chart.js`, тому збірка з нуля або впаде на резолві ресурсу, або дасть неповний пакет.

Додатковий нюанс: код графіки імпортує `chart.js` **з npm** (`modules/stats_chart_data.ts:8` → `import { Chart } from 'chart.js/auto'`), а не з `lib/`. Тобто локальна копія `lib/chart.js` (208 КБ) — дубль залежності, який ніхто не завантажує.

**Напрямок фіксу:** прибрати `lib/chart.js` із `web_accessible_resources` і видалити файл (npm-залежність уже покриває потребу); або, якщо копія потрібна, зняти `lib/` з `.gitignore` і закомітити.

---

#### C3. Невикористаний дозвіл `scripting` у маніфесті
**Файл:** `manifest.json:13`

Інвентаризація всіх викликів `chrome.*` по кодовій базі: `storage.local` (18), `storage.onChanged` (8), `runtime.onMessage` (7), `runtime.id` (7), `tabs.query` (4), `runtime.sendMessage` (3), `action.*` (7), `runtime.getURL` (1). **`chrome.scripting` не викликається жодного разу.**

Зайвий дозвіл — це і додаткова поверхня атаки, і типова причина причіпок на рев'ю Chrome Web Store («запитано дозвіл, який не використовується»).

**Напрямок фіксу:** видалити `"scripting"` з `permissions`. (`activeTab` теж надлишковий — потрібні origin'и вже покриті `host_permissions` — але він нешкідливий і його можна лишити.)

### 🟡 S2. `isExtensionContextInvalidated` — два варіанти з різною поведінкою на збої

## 5. Висновок

Проєкт у **доброму інженерному стані**: статичні перевірки чисті, 1959 тестів зелені, збірка робоча, архітектура дрібномодульна, небезпечних патернів виконання коду немає.

Критичних дефектів не знайдено. З трьох знахідок середньої важливості дві — **пакувальні** (C2, C3) і б'ють по релізу в Chrome Web Store, а не по рантайму; одна (C1) — реальний, відтворений баг рендера з чіткою умовою спрацювання.

SSOT на рівні **архітектури** (сховище, селектори, сервіси, адаптери) дотриманий строго — це найсильніша частина проєкту. Порушення залишились лише на рівні **дрібних хелперів**, які обійшли увагу рефакторингу: з них S1 (`cleanAuthorName`) має доведений вплив на дані користувача, решта — латентні пастки.

**Пріоритет робіт:**
1. **C2** — інакше збірка з чистого клону неповна (найдорожча помилка з трьох).
2. **S1** — розщеплення груп авторів у попапі; єдине порушення SSOT, що вже псує вихідні дані.
3. **C3** — прибрати `scripting` перед подачею в CWS.
4. **C1** — переписати підсвітку на один прохід.
5. **S2**–**S4**, **N3** — звести хелпери-дублікати до канону.
6. **N2** + **N7** — централізувати версію та вичистити корінь; далі решта N.
