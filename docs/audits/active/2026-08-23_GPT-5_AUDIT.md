# Аудит YouTube / YouTube Studio модуля

**Дата:** 2026-08-23  
**Модель:** GPT-5  
**Обсяг:** `youtube/`, з акцентом на `youtube/studio/`, пов'язані `CommentService` / `CommentInjector`, тести `studio_*` і `yt_*`.

## Підсумок

Модуль не варто переписувати з нуля. У ньому вже є корисний каркас: платформні адаптери, централізований `CommentService`, rAF-дедуплікація, capture-phase scroll для Polymer, виявлення recycling за `commentKey`, централізований DOM observer і коректне читання emoji через `img[alt]`.

Однак поточну версію не можна вважати стабільною для довгих сесій і масштабування. Основні проблеми лежать не у розмірі функцій, а в життєвому циклі, володінні event listener-ами, синхронізації кешів та реальних інтеграційних сценаріях. Зелені тести переважно перевіряють окремі функції й частково фіксують стару поведінку, але не доводять коректність повного циклу `init → scroll/recycle → storage change → stop → start`.

## Критичні знахідки

### P0. Studio ігнорує початкове `studio_enabled: false`

- `StudioStorageController.enabled` починається з `true`: `youtube/studio/studio_storage_handler.ts:17`.
- Реальний entrypoint викликає `initializeStudioModule(...)`: `youtube/studio/studio_content.ts:30-41`.
- `initializeStudioModule` читає ключ `STUDIO_ENABLED`, але ніде не переносить його в controller: `youtube/studio/studio_init.ts:42-63`.
- Метод `StudioStorageController.loadStorageData()`, який правильно встановлює `enabled`, при первинній ініціалізації не викликається: `youtube/studio/studio_storage_handler.ts:63-83`.

Наслідок: якщо Studio-модуль вимкнули раніше, після завантаження сторінки він однаково стартує. Вимкнення спрацює лише після нової storage-події.

Рекомендація: залишити одне джерело boot-state — `StudioStorageController.loadStorageData()` або окремий `StudioStateStore.loadSnapshot()`. Не мати двох різних завантажувачів стану.

### P0. `stop → start` створює видимий, але частково «мертвий» UI

Studio cleanup видаляє:

```text
.syh-studio-btn, .syh-studio-video-meta, .syh-header-counters-wrapper
```

див. `youtube/studio/studio_comment_processor.ts:132-135`.

Production UI насправді створює `.syh-studio-badge-wrapper` і `.syh-studio-checkbox-wrapper`: `youtube/studio/studio_ui.ts:61-115`. Клас `.syh-studio-video-meta` цим кодом не додається. Також cleanup не скидає `data-syh-studio-events-bound`.

Після повторного старту кнопки створюються заново, але тред лишається позначеним як уже bound. `CommentInjector` бачить прапорець і не вішає listeners: `modules/comment_injector.ts:24-26`. У результаті кнопки можуть бути видимі, але не реагувати.

Аналогічна проблема є у звичайному YouTube: `cleanupYouTubeUI()` видаляє лише `.syh-yt-buttons`, але лишає `data-syh-yt-events-bound`, `.syh-yt-comment-body` і `.syh-yt-comment-checked`: `youtube/yt_init.ts:59-62`. Після re-enable нова панель може не отримати події.

Рекомендація: cleanup має бути симетричним init і прибирати всі створені вузли, класи, dataset-прапорці, observers та listener-и. Додати обов'язковий regression test `start → stop → start → один клік = одна дія`.

### P0. Polymer recycling накопичує event listener-и

- При зміні `commentKey` cleanup прибирає лише dataset-прапорці й original text: `youtube/studio/studio_binding_state.ts:37-50`.
- Реальні listener-и з кнопок/тіла треду не знімаються.
- Наступний bind знову викликає `addEventListener`: `modules/comment_injector.ts:31-39`.
- `ensureToolbarActionButtons()` перевикористовує існуючі кнопки, якщо всі вони є: `youtube/studio/studio_ui.ts:20-58`.

Тому один і той самий DOM-вузол iron-list після кількох recycling-циклів може мати кілька click/change/contextmenu handler-ів. Один клік тоді запускає кілька асинхронних toggle/save операцій. Це високовірогідне пояснення проблем, які з'являються після довгого скролу або збільшення кількості коментарів.

Рекомендація: перейти на одну з двох моделей:

1. event delegation на стабільному кореневому контейнері/window з обчисленням актуального context у момент події; або
2. `AbortController` на recycled-вузол: `abort()` перед повторним bind і при stop.

Dataset-прапорець не є керуванням ресурсами й не може замінити відписку.

## Високі ризики

### P1. Ініціалізація Studio не ідемпотентна, підписки не мають повного cleanup

- Поле `isInitialized` оголошене, але не читається і не змінюється: `youtube/studio/studio_content.ts:13`.
- Кожен `init()` створює новий storage callback: `youtube/studio/studio_content.ts:30-41`.
- `SYH_STORAGE.onChanged()` не повертає unsubscribe і facade не має `offChanged`: `modules/storage_keys.ts:22`, `modules/storage_runtime.ts:29-40`.
- `StudioSPAHandler.start()` додає анонімні `popstate` і `yt-navigate-finish` callbacks: `youtube/studio/studio_spa_handler.ts:11-20`.
- `stop()` очищає тільки interval і не викликає `removeEventListener`: `youtube/studio/studio_spa_handler.ts:23-28`.

Наслідок: повторний init або майбутнє підключення експортованого plugin API накопичує callbacks. Навіть після destroy старі callbacks можуть викликати controller.

Рекомендація: controller-state machine `stopped | starting | running | stopping`, один `initPromise`, іменовані callbacks, unsubscribe для storage, повністю симетричний `destroy()`.

### P1. Відкладений `MutationObserver` може пережити stop і повторно ін'єктувати UI

- На кожному incomplete comment metadata створюється observer: `youtube/studio/studio_video_metadata.ts:87-108`.
- `stopModule()` не обходить треди й не викликає `disconnectVideoMetadataObserver()`.
- Callback observer-а без перевірки `enabled` повторно викликає `bindStudioCommentEvents`: `youtube/studio/studio_events.ts:97-99`.

Наслідок: після вимкнення/навігації delayed metadata може знову запустити bind. Окрім цього, `hasVideoMetadata()` вважає достатнім title **або** href, тоді як complete вимагає обидва (`studio_video_metadata.ts:55-80`), що створює зайві цикли disconnect/rebind під DOM-мутаціями.

Рекомендація: централізоване володіння observers у processor, abort/generation token у callback, disconnect усіх observers під час stop.

### P1. Лічильники header працюють зі старим `sheetStatsMap`

- `StudioCommentProcessor` отримує початковий object reference у constructor: `youtube/studio/studio_content.ts:23-27`.
- Після storage reload controller замінює весь object: `youtube/studio/studio_storage_handler.ts:80-82`.
- Processor про новий object не дізнається; `setSheetStatsMap()` існує, але production-код його не викликає.

Наслідок: після зміни collected items header може перемальовуватись зі старими числами.

Рекомендація: стабільний store object із mutation-in-place або явна subscription/update перед render. Не зберігати окрему копію стану в `StudioHeaderUpdater`.

### P1. Storage-події створюють зайві повні reload-и та можливі lost updates

- Для кожного зміненого collected-key запускається окремий повний `loadStorageData()`: `youtube/studio/studio_storage_handler.ts:53-59`.
- Якщо одна storage-подія містить кілька collected-key, цикл запускає кілька паралельних повних reads: `studio_storage_handler.ts:85-90`.
- `setStudioVideoSheetOverride()` робить read-modify-write через `getAsync()` + `setAsync()`, а не через доступний `updateAsync()`: `youtube/studio/studio_video_map.ts:39-84`.

Наслідок: write amplification при bulk-операціях і ризик втрати ручного override/log entry у двох вкладках або при швидких діях.

Рекомендація: coalesce storage changes в один microtask/rAF reload; video map/log змінювати атомарно через `SYH_STORAGE.updateAsync([mapKey, logKey], ...)`.

### P1. Звичайний YouTube прив'язує handler-и до застарілих cache references

`bindYTEvents()` створює новий wrapper і копіює поточні references `buttonStates`, `checkboxStates`, `collectedList`: `youtube/yt_events.ts:39-55`. Storage handler пізніше замінює ці objects/array у `stateCache`: `youtube/yt_storage_handler.ts:31-47`. Уже прив'язані `CommentInjector`-и продовжують працювати зі старими references.

Наслідок: після зовнішньої storage-зміни UI може показати новий стан, але наступний клік збереже дані зі старого cache snapshot і перезапише актуальні зміни.

Рекомендація: передавати один стабільний store/caches object, властивості якого оновлюються централізовано; не створювати per-comment cache wrapper.

## Середні ризики та масштабування

### P2. Ідентичність коментаря недостатньо надійна

- Studio key залежить від `videoTitle + author + text`: `youtube/studio/studio_comment_key.ts:11-22`. Зміна title/text змінює identity; однакові коментарі того самого автора на одному відео матимуть той самий key.
- YouTube fallback хешує лише автора і перші 20 символів тексту: `youtube/yt_comment_identity.ts:39-56`. При великій кількості однотипних коментарів колізії стають реальним ризиком.

Рекомендація: пріоритет реальному comment id/permalink; fallback — versioned full normalized identity із video id та повним текстом. Зберігати `identityVersion` для майбутньої міграції.

### P2. «Пріоритет» selector fallback фактично не є пріоритетом

Масив selector-ів склеюється у CSS-group і передається одному `querySelector`: `youtube/studio/studio_selector_queries.ts:18-37`. Перемагає перший вузол у DOM, а не перший selector у масиві. Код сам документує цей quirk у `studio_selector_constants.ts:8-11`, а тести його фіксують.

Наслідок: після змін DOM YouTube більш загальний fallback може перехопити чужий `#toolbar`, `#name` або `#metadata`.

Рекомендація: перебирати selector-и послідовно; для кожного getter-а мати sanitized DOM fixture з реальною структурою Studio.

### P2. Дані, що ростуть, не мають повної retention-політики

- `STUDIO_OVERRIDE_LOG` обмежений 500 записами, але video map не має TTL/ліміту: `youtube/studio/studio_video_map.ts:51-84`.
- Global cleanup чистить checkbox states, але не Studio/YouTube button states і не video map: `modules/retention_service.ts:81-110`.
- У manifest немає `unlimitedStorage`: `manifest.json:11-15`.

Рекомендація: schema/version + TTL/LRU для video map, cleanup button state разом із collected item, quota telemetry та контрольований recovery при storage error.

## Оцінка тестів

### Що пройшло

- Studio subset: **215/215**.
- Повний suite: **1959/1959**.
- `npm run typecheck`: успішно.
- `npm run lint`: успішно.
- `npm run build`: успішно, 279 modules transformed.

### Чому зеленого suite недостатньо

1. `studio_content.ts` — реальний controller/entrypoint — взагалі не з'явився у coverage report, тобто основний lifecycle не тестується.
2. `studio_init.ts`: 32.81% lines, 0% functions у Studio coverage.
3. `studio_video_map.ts`: 33.71% lines; `studio_binding_events.ts`: 62.92%; `studio_comment_processor.ts`: 71.34%.
4. Coverage threshold у scripts відсутній; test script вручну перелічує файли. Новий test-файл може не запускатись, доки його явно не додадуть у `package.json`.
5. Є багато characterization/`doesNotThrow` перевірок. Наприклад `setCaches / setSheetStatsMap` перевіряються лише на відсутність винятку: `tests/studio_comment_processor.test.js:104-115`.
6. SPA stop-test перевіряє тільки `clearInterval`, але не `removeEventListener`: `tests/studio_spa_handler.test.js:43-57`.
7. Cleanup-test створює `.syh-studio-video-meta`, якого production UI не створює, і не перевіряє реальні badge/checkbox wrappers: `tests/studio_comment_processor.test.js:79-92`.
8. Тест звичайного YouTube прямо очікує observer при вимкненому модулі: `tests/yt_bootstrap.test.js:312-321`. Це приклад фіксації небажаної поведінки замість бізнес-вимоги.
9. Немає браузерного сценарію з реальним iron-list/recycling, повторним enable/disable, SPA navigation і перевіркою «один клік = один storage write».

Висновок щодо тестів: helpers і чисті правила покриті непогано, але тести слабко захищають саме ті сценарії, що визначають стабільність масштабованого DOM-модуля.

## Рекомендований план доробки

### Етап 1 — спочатку regression-тести на реальні дефекти

1. `studio_enabled=false` на boot не запускає processor/observer/UI.
2. Подвійний `init()` створює рівно одну storage і SPA subscription.
3. `destroy()` прибирає всі subscriptions, timers, observers та callbacks.
4. `start → stop → start`: кожна кнопка працює; один клік дає одну дію.
5. Recycling `A → B → C` на тому самому DOM-вузлі: listener count не росте; один клік дає один storage write для C.
6. Pending metadata observer після stop нічого не ін'єктує.
7. Зміна collected storage оновлює реальні цифри header.
8. Одна storage-подія з кількома collected-key робить один reload/render.
9. Два паралельні manual override не гублять map/log updates.
10. Повторити аналогічний enable/disable/cache test для звичайного YouTube.

### Етап 2 — переробити lifecycle, не бізнес-логіку

- Один controller/store на платформу.
- Ідемпотентні `start()` / `stop()`.
- `AbortController` або централізований registry для DOM listeners.
- Unsubscribe-контракт для storage.
- Generation token для всіх async callbacks.
- Симетричний UI cleanup.

### Етап 3 — event delegation та стабільний state store

- Події кнопок/checkbox обробляти через один стабільний handler, який читає актуальний context у момент події.
- Не прив'язувати comment identity до closure.
- Усі button/checkbox/category states отримувати через адаптер/сервіс, відповідно до правила Single Source of Truth.
- HeaderUpdater має читати поточний snapshot store, а не тримати власну копію map.

### Етап 4 — storage і довгі сесії

- Coalescing storage events.
- Атомарні update-и.
- TTL/LRU для video map/button states.
- Метрики: кількість active listeners/observers, processed comments per frame, storage read/write failures, processing duration.

### Етап 5 — реальний браузерний smoke

Перед зміною DOM-логіки потрібен DevTools trace на актуальній сторінці Studio: структура parent/reply, recycling одного вузла, listener count до/після скролу, поведінка після disable/enable. Після цього зафіксувати sanitized HTML fixtures та мінімальний manual/browser smoke checklist.

## Пріоритет рішення

Не робити ще один великий «Fallow refactor» лише за метриками complexity. Спочатку виправити три наскрізні інваріанти:

1. **Один lifecycle:** повторний start/stop не змінює кількість ресурсів.
2. **Одна дія:** один user event завжди дає одну domain/storage operation.
3. **Один стан:** UI завжди читає актуальний snapshot через service/adapter.

Після цього модуль можна масштабувати без повного переписування.

## Обмеження аудиту

- Це статичний аудит і локальні automated checks; реальний DOM поточної версії YouTube Studio не інспектувався.
- Runtime-симптом користувача ще не зіставлений із DevTools trace, тому перед правками DOM-поведінки потрібне фактичне відтворення.
- `RTK.md`, на який посилається `AGENTS.md`, у workspace і батьківських шляхах не знайдено.
