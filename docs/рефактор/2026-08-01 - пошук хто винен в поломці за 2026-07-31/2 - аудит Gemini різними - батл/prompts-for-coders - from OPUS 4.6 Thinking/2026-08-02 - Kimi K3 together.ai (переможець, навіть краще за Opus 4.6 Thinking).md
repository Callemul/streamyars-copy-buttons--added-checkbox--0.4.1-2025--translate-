# Коротка відповідь: ділити самому. Файл `phase-1_critical-bugs.md` — це правильний патерн.

Давати кодеру весь `TASKS.md` — погана ідея з трьох причин:

1. **Деградація уваги.** 19 задач у контексті — модель читає про M4 (namespacing) і L4 (jQuery), коли працює над H1. Це пряма втрата якості на довгому контексті.
2. **Scope creep.** Агент з повним списком неминуче почне «попутно» чіпати задачі поза скоупом, ламаючи ваш граф залежностей (наприклад, зробить M2 до H5).
3. **Токени.** Повний файл ≈ у 3–4 рази більший за фазовий. Ви платите за це в кожній сесії, плюс модель витрачає reasoning tokens на переосмислення непотрібного.

`TASKS.md` залишається **майстер-трекером для вас** (чекбокси, статуси). Кодер його взагалі не бачить.

## Як покращити поточний підхід

### 1. Дрібніше: не по фазах, а по групах файлів

Фаза 1 на ~8 год — це 3 окремі сесії, які можна гнати **паралельно** (різні файли — нуль конфліктів):

| Сесія | Задачі | Файл | Чому разом |
|:--|:--|:--|:--|
| 1A | H1 + H3 | `studio_events.ts` | Один файл, H1 перед H3 |
| 1B | H2 + L2 | `stats_tracker.ts` + temp | Швидка сесія ~40 хв |
| 1C | H4 | `stats_exporter.ts` | Незалежна |

### 2. Перегляньте Фазу 2 — там є марна робота

**L7 (debounce у `popup_init.js`) у Фазі 2 — викинуті гроші.** Цей файл у Фазі 3 буде повністю переписаний на TS. Перенесіть L7 у сесію 3A. Те саме стосується M1 — ваш файл сам зазначає, що M2 закриє її автоматично.

### 3. Фазу 3 — по одному файлу за сесію, і злити H5+L5+M2 в один прохід

План «спочатку модулі, потім storage» змушує **двічі** перечитувати і переписувати ті самі файли. Економніше:

- **3A:** `popup_init.js` → `.ts` + ES-модулі + одразу через `SYH_STORAGE` + L7 + L9 + L10 (все в одному файлі!)
- **3B:** `popup_telegram.js` → те саме
- **3C:** `popup_prayers.js` → те саме
- **3D:** M4 namespacing + міграція (окремо, бо ризик втрати даних)

Трейдофф: більший крок важче верифікувати, але ви економите повний цикл «прочитав → змінив → протестував» на кожен файл.

## Оптимізація токенів у промпт-файлах

**Що ВИКИНУТИ** (у `phase-1` це вже зроблено — добре):
- Mermaid-діаграми, статус-таблиці, дорожні карти — це для людей
- `file:///d:/Chrome%20Extension/...` посилання — сотні токенів сміття. Тільки відносні шляхи: `youtube/studio/studio_events.ts`

**Що ЗАЛИШИТИ:**
- Сніпети «❌ ЗАРАЗ / ✅ ПІСЛЯ» — це головний економувач reasoning tokens. Модель не виводить рішення сама, а верифікує готове → менше міркувань, менше варіативності, вища якість.

**Що ДОДАТИ** (компактний хедер ~10 рядків у кожен файл):

```markdown
## Контекст
Chrome Extension MV3, Vite + TS. Верифікація: npm run lint && npm run test && npm run build

## Скоуп
Читай і змінюй ТІЛЬКИ: youtube/studio/studio_events.ts
Номери рядків приблизні — шукай за іменем функції.
Якщо код не збігається з описом — зупинись і доповідь, не вигадуй.

## Формат звіту
- Змінено: файл → функція
- Кожен критерій приймання: ✅/❌
- Вивід команди верифікації
```

Рядок «якщо код не збігається — зупинись» критичний: рядки в `TASKS.md` з часом роз'їдуться, і без цього агент почне «творчо інтерпретувати».
