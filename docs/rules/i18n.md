# Правило i18n: повний інтерфейс uk / en / ru

Статус: конвенція C4.5b, 2026-09-11; реалізація — наступні хвилі C4.5c.
Інвентар і межі — [i18n-inventory.md](../plans/i18n-inventory.md).
Користувач обрав повну локалізацію трьома мовами. Цей документ не означає,
що перемикач мови або наведені нижче розширення API вже реалізовані.
Рядок у §5 AGENTS.md має додати власник того файла окремо: поточний мандат
дозволяє змінювати лише цей документ та інвентар.

## 1. Новий видимий рядок = ключ у messages.json

Кожний новий текст, який створює розширення для користувача, отримує ключ
в усіх трьох `_locales/{uk,en,ru}/messages.json` в тому самому коміті.
Це підписи, заголовки, tooltip, placeholder, aria-label, alt, document.title,
confirm/alert/toast, повідомлення про помилки, порожні стани, підписи графіків,
canvas/PNG, читабельні звіти та пояснення у видимих журналах.
Однаковий зміст і контекст використовують один ключ; однакове слово з різною
семантикою може мати різні ключі. Каталог не містить HTML, CSS або селекторів.

Виклики перекладу йдуть через `modules/registry/i18n.ts`, а не прямий
`chrome.i18n.getMessage` у компонентах. Ключі підписів дій належать записам
`modules/comments/comment_actions.ts`; ключі вбудованих аркушів — записам
`modules/registry/sheets.ts`. Не створювати паралельний реєстр кнопок чи аркушів.
Переклад не змінює `id`, `data-action`, `stateType`, категорію, storage key або
`null` для дії, недоступної на поверхні.

## 2. Межа UI / дані / інтеграція

- Не перекладати введений текст, авторів, міста, заголовки відео, назви каналів,
  користувацькі назви аркушів, шаблони назв програм, уже збережені результати.
- Не перекладати regex, тригери, транслітераційні таблиці, псевдоніми каналів,
  назви фаз у схемі, анонімні sentinel-значення та ключі дедуплікації.
- Не локалізувати під UI-мову заголовки Telegram/молитов, `data-template`
  банерних чіпсів, розділювач банерів або канонічний текст копіювання відео.
  Це вихідний контент/формат даних; зміна його мови потребує окремого контракту.
  Локалізується підпис кнопки, що створює цей контент.
- `console.*`, технічні винятки та внутрішні журнали не потребують перекладу.
  Але назва змінної `log` чи префікс `[SYH]` не є доказом: якщо рядок доходить
  до DOM, toast або користувацького звіту, його обгортка належить UI.
- Текст сайту, за яким шукаємо кнопку, — інтеграційний токен. Зокрема
  `stayInStudio`, `download`, `timerOff` не можна автоматично прив'язувати
  до обраної користувачем мови розширення. Мова сайту може бути іншою.
  Зберігати наявні fallback-правила пошуку; не вгадувати нові селектори.

Для змішаного рядка перекладати лише обгортку, передаючи дані параметрами.
Вбудований підпис аркуша можна локалізувати за його стабільним id, але не
переписувати збережене `label` користувацького аркуша. Замінити текстові
`.replace()` для жирних фрагментів Studio на структурований рендер за id.

## 3. Імена та формат каталогу

Нові ключі: ASCII `lower_snake_case`, схема `zone_entity_purpose`:
`popup_prayers_empty`, `options_save_success`, `comments_prayer_add_title`,
`banners_delete_confirm`, `stats_viewers_label`, `studio_category_manual_title`.
Зони: `common`, `popup`, `options`, `comments`, `banners`, `stats`, `studio`,
`video`, `sheets`. Не кодувати в ключі мову, текст перекладу або номер рядка.
Існуючі 13 camelCase-ключів зберігати: окреме перейменування не є передумовою.
Наявний ключ використовувати лише після звірки змісту: `tabTelegram` зараз
не згадує YouTube, хоча актуальна вкладка його згадує.

```json
{
  "banners_create_count": {
    "message": "Створити банери ($COUNT$)",
    "description": "Banner modal submit button; count is the number of preview banners.",
    "placeholders": { "count": { "content": "$1", "example": "12" } }
  }
}
```

Імена placeholder та їх позиції однакові в uk/en/ru. Речення перекладається
цілком; не складати його з перекладених відмінків `питань` + `молитов` чи
`банерів` + назва вкладки. Значущі пробіли й пунктуація належать повідомленню.
Символи/іконки без мовного змісту можуть залишатися в коді; доступний підпис
іконки обов'язково має ключ.

## 4. Поточний контракт та наступна основа повного i18n

Зараз `I18nAdapter.getMessage(key: string, fallback?: string): string` викликає
Chrome, перехоплює недоступний extension context і повертає fallback або `''`.
Залишити цю сигнатуру та синхронний результат сумісними. Другий аргумент
не можна перевизначати як substitutions: існуючі виклики передають fallback.

На поточній хвилі `i18n.ts` лишається незмінним за уточненням користувача.
Наведені далі доповнення — окрема наступна задача для explicit locale та
параметрів, не вимога до DOM-helper і не вже доступний API.
Запропоновані доповнення **до тієї ж реалізації**:

```ts
type UiLocale = 'uk' | 'en' | 'ru';
type LocalePreference = UiLocale | 'auto';
// Нові exports, не новий незалежний сервіс перекладу:
configureLocale(preference: LocalePreference, browserLanguage: string): void;
getLocale(): UiLocale;
// Третій аргумент додається без зміни значення другого:
getMessage(key: string, fallback?: string, substitutions?: string | string[]): string;
```

Каталоги завантажувати як bundled JSON із `_locales`, без мережі та без
окремих ручних TS-словників. `tsconfig.json` зараз не має `resolveJsonModule`:
додати підтримку JSON-імпортів і перевірити Vite build та Node test loader
перед міграцією споживачів. Самі JSON залишаються SSOT. Для ключів вивести
`MessageKey` із default-каталогу для нових descriptors/DOM bindings; зберегти
сумісну string-сигнатуру старого `I18nAdapter`, захистити її перевіркою ключів.

Реалізація substitutions у bundled-каталогах має відтворити формат Chrome
для використовуваного піднабору: `$NAME$` → placeholder.content → `$1`…,
буквальний `$` через `$$`. Однопрохідне вставлення значень: дані користувача
не інтерпретуються повторно як placeholder. Перевіряти контракт тестами.
Для числа з відмінюванням додати централізований helper у цьому ж модулі:
`Intl.PluralRules(getLocale())` → ключі `_one/_few/_many/_other`; кожна
локаль містить усі оголошені варіанти (англійські невживані можуть повторювати
`other`). Параметризовані нейтральні підписи `Питання: $COUNT$` бажані, де доречні.
Форматувати показані числа/дати через Intl з `getLocale()`; не міняти ISO-дати,
ключі статистики, збережений таймер або машинні поля експорту.

## 5. Вибір мови, fallback і життєвий цикл

Використовувати наявну опцію `ui_locale` з `OPTION_FIELDS` та
`STORAGE_KEYS.OPTIONS`; не вводити другий storage key. Значення `uk/en/ru`
має пріоритет. Для `auto` нормалізувати мову браузера (`en-US` → `en`,
`uk-UA` → `uk`, `ru-RU` → `ru`); непідтримувану/порожню → `uk`, як
`manifest.json.default_locale`. Невалідну збережену опцію читати як `auto`,
не переписуючи сховище. `navigator.language` — резерв, коли Chrome API нема.

Після конфігурації UI lookup: каталог обраної локалі → каталог uk →
явний legacy fallback → видимий `[missing:key]`. Порожній message вважається
відсутнім. Повнота каталогів перевіряється до релізу; production UI не має
тихо ставати порожнім. До configureLocale працює детермінований auto lookup
на bundled-каталогах. Втрата Chrome context не ламає вже відкритий UI.
Збережені віконні експорти `window.SYH_I18N` не видаляти в цій міграції.

Не додавати імпорт storage/options/core у `registry/i18n.ts`: це створить
зворотні залежності реєстрів. Наявні entry-point orchestration-модулі читають
опції через `SYH_STORAGE` і передають їх у configureLocale **до першого
рендеру** popup/options/трьох content scripts. Не читати Chrome storage
всередині getMessage та не визначати мову за DOM стороннього сайту.

Для першого релізу: збереження мови локалізує options після успішного save;
popup використовує її при наступному відкритті; уже відкриті StreamYard,
YouTube і Studio — після перезавантаження вкладки. Додати перекладене
повідомлення про це на options. Не перезавантажувати вкладки автоматично.
Підпис на зміни мови з живим перемальовуванням усіх поверхонь — окреме
розширення контракту; воно не потрібне для початкової повної локалізації.

Перед зміною поведінки getMessage винести інтеграційний lookup трьох старих
ключів в явно відокремлений метод того самого адаптера, який зберігає Chrome
lookup і старі fallback. Це не другий словник UI і не переклад DOM сайту.
Звірити anti-AFK dependency injection. Перевірити сценарій UI=en / сайт=ru.

## 6. HTML та динамічний DOM

За уточненням користувача DOM-helper — `modules/dom/localize.ts`,
експорт `localize(root: ParentNode)`, імпорт `modules/registry/i18n.ts`.
Реалізацію helper і його тестів веде користувач; цей документ їх не змінює.
Контракт — лише чотири атрибути:

| Атрибут | Призначення | Fallback при відсутньому перекладі |
|---|---|---|
| `data-i18n` | `textContent` | поточний текст вузла |
| `data-i18n-title` | `title` | поточне значення title |
| `data-i18n-placeholder` | `placeholder` | поточне значення placeholder |
| `data-i18n-aria-label` | `aria-label` | поточне значення aria-label |

Значення data-атрибута — ключ каталогу. Helper використовує чинний
`SYH_I18N.getMessage(key, currentString)`; **ніякого innerHTML**.
Він не керує locale, сховищем, listeners або життєвим циклом.
`alt`, document.title та інші текстові властивості, що не входять до
контракту helper, обробляти явно через той самий адаптер. Не вводити
непідтримуваний `data-i18n-alt`. Подальша fallback-політика §5 потребує
окремої адаптерної зміни; зараз відсутній переклад лишає поточний рядок.

Для popup/options викликати `localize(document)` перед показом UI.
Коли реалізовано §4–5 — після configureLocale. У popup окремо
обробити `template.content` **до клонування**, або кожний клон перед вставкою:
querySelectorAll(document) не обходить вміст `<template>`. Рекомендовано
локалізувати клон у `popup_sheet_renderer.ts`, щоб усі аркуші отримали підписи.
Повторний виклик не додає listeners і не змінює значення полів.

Не ставити `data-i18n` на контейнер з `<b>`, кнопкою, лічильником, input або
іконкою: textContent знищить дітей. Виділити span для підпису; змінні
лічильників лишити окремими вузлами з чинними id/classes. Не перекладати
contenteditable-результат чи textarea.value після відновлення даних.
Після тимчасового `Скопійовано`/помилки відновлювати перекладений idle-підпис.

У TS-шаблонах використовувати textContent/DOM API, або escapeHtml/escapeAttr
для результату getMessage і підставлених значень у відповідному контексті.
Не використовувати innerHTML для рядка з каталогу. Жирні фрагменти/посилання
будувати розміткою з окремими локалізованими текстовими вузлами.
Встановлювати `document.documentElement.lang` тільки в документах розширення
і generated HTML-звіті; у content script — `lang` на власному UI-контейнері.

## 7. Видимі діагностики та перевірка

Парсер повертає код помилки/тип діагностики та параметри; renderer переводить
їх у ключ. Не імпортувати браузерний translator у чистий парсер. Зберегти
сумісність legacy log/error shape на час переходу та читання старих saved logs.
Виведений сирий текст користувача лишається даними. Не замінювати перекладом
рядки, за якими працює дедуплікація або пошук; не переписувати історичні logs.

Після кожної зони: `npm run verify` (через rtk за локальним workflow), плюс
візуальна перевірка цієї зони в uk/en/ru. Перевірити довгі tooltip/aria-label,
порожній/заповнений стан, помилку, підтвердження видалення та reset-підписи.
Для основи потрібні змістовні тести: parity ключів/placeholder, auto та explicit
locale, missing/empty key, відсутній Chrome, підстановка `$`/лапок/`<>&`, plural
0/1/2/5/11/21, повторна DOM-локалізація, template clones, збереження дітей і
користувацьких даних. Для shared actions — всі три поверхні й незмінні id.
Для аналітики — також PNG/HTML/MD/CSV. Для runtime-імпортів — відсутність
значеннєвих циклів між доменами. Збіги кирилиці самі по собі не є провалом.
