# Вибір моделей і рівня мислення в Codex

> Проєктний довідник для користувача, root-агента та субагентів  
> Актуально на: 2026-08-23

## 1. Коротка відповідь

Якщо немає часу класифікувати задачу:

- **один універсальний рівень мислення:** `High`;
- **одна універсальна конфігурація з пріоритетом якості:** `gpt-5.6-sol` + `High`;
- **щоденний економніший default для чітко обмеженої реалізації:** `gpt-5.6-terra` + `High`.

Це компроміси, а не оптимум для всіх ситуацій. Для критичної архітектури потрібен Sol з `Extra High`, а для механічної роботи достатньо Luna з `Medium`.

## 2. Головне правило вибору

Вибір визначає не розмір тексту задачі, а її ризик і зв'язність:

| Характер задачі | Модель | Рівень |
|---|---|---|
| Архітектура, кілька модулів, неоднозначність, lifecycle, race conditions, масштабування | `gpt-5.6-sol` | `High` або `Extra High` |
| Чітка реалізація в обмеженому наборі файлів, локальний review, DOM/storage integration | `gpt-5.6-terra` | переважно `High` |
| Вузька, детермінована, повторювана або механічна робота | `gpt-5.6-luna` | `Medium` |

Не обирати слабшу модель лише тому, що задача називається «тести» або «маленький fix». Тестування race condition, lifecycle чи міграції identity може бути складнішим за саму реалізацію.

## 3. Що означають назви моделей у цьому проєкті

### `gpt-5.6-sol` — складне наскрізне мислення

Використовувати, коли агент повинен:

- спроєктувати або змінити shared API;
- простежити стан через кілька сервісів і модулів;
- знайти причину проблеми, яка проявляється лише після масштабування;
- працювати з lifecycle `start → stop → start`, SPA-навігацією або відновленням стану;
- розв'язати race condition, lost update, дублювання listener/observer;
- спроєктувати стабільну identity, migration або deduplication;
- провести фінальне інтеграційне чи архітектурне рев'ю;
- приймати рішення за неповної або суперечливої інформації.

Не витрачати Sol на просте перейменування, форматування, inventory тестів або створення очевидних fixtures.

### `gpt-5.6-terra` — обмежена реалізація і практичний review

Використовувати, коли:

- архітектурне рішення вже прийняте;
- задача має чіткі acceptance criteria;
- ownership файлів визначений і не перетинається з іншими агентами;
- треба реалізувати локальну DOM-, state- або storage-інтеграцію;
- треба зробити read-heavy exploration або review обмеженого subsystem;
- треба написати тести для одного сервісу з уже відомим контрактом;
- треба діагностувати UI після отримання фактичних DevTools-логів.

Не доручати Terra самостійно змінювати фундаментальну identity, lifecycle або event ownership, якщо межі рішення ще не визначені.

### `gpt-5.6-luna` — вузька повторювана робота

Використовувати, коли задача:

- однозначна і має точний шаблон результату;
- не вимагає архітектурного рішення;
- не змінює shared contract;
- легко перевіряється автоматично;
- складається з inventory, fixtures, табличної перевірки або документації;
- має великий обсяг однотипних незалежних операцій.

Приклади: знайти всі наявні тести за шаблоном, доповнити механічні fixtures, звірити список exports, оформити вже ухвалене рішення.

Не доручати Luna пошук причин нестабільності, concurrency, Polymer recycling, storage races або фінальне correctness-review.

### Примітка про `gpt-5.6` і `gpt-5.6-sol`

Офіційна документація називає сильну модель для складної багатокрокової роботи `gpt-5.6`. У поточному середовищі Codex найсильніший agentic coding-варіант доступний як `gpt-5.6-sol`. У цьому документі **Sol означає вибрати найсильніший доступний GPT-5.6 coding-варіант**.

## 4. Вибір рівня мислення

| Рівень у Codex | Значення в конфігурації | Коли використовувати |
|---|---|---|
| Light / Low | `low` | лише очевидна read-only або механічна дія, де помилку легко помітити |
| Medium | `medium` | чітка вузька задача, fixtures, inventory, документація, bounded tests |
| High | `high` | основний рівень для реалізації, review, складної логіки та edge cases |
| Extra High | `xhigh` | критична архітектура, lifecycle, concurrency, identity, migration, фінальне рев'ю |
| Max | `max` | лише особливо складний підтверджений випадок, який не вдалося надійно закрити на `xhigh` |
| Ultra | `ultra` | найглибше мислення на підтримуваних моделях; не є default цього проєкту |

### Просте правило

- Не знаєте, який reasoning вибрати → **High**.
- Задача повністю детермінована й локальна → **Medium**.
- Помилка виникає під навантаженням, після повторного запуску або через кілька джерел стану → **Extra High**.
- `Max/Ultra` не компенсують нечітке ТЗ, відсутні DevTools-факти чи погане розбиття задачі.

Вищий reasoning збільшує час виконання і використання токенів. Його треба підвищувати через складність, а не «про всяк випадок».

## 5. Алгоритм вибору за 30 секунд

Відповідайте зверху вниз. Перша відповідь «так» визначає конфігурацію.

1. Чи є concurrency, lifecycle, identity, migration, shared API або проблема після масштабування?  
   **Так → Sol + Extra High.**

2. Чи треба прийняти неоднозначне рішення, яке вплине щонайменше на три модулі або багато викликів?  
   **Так → Sol + High.** Якщо ризик регресії високий — Extra High.

3. Чи архітектура вже визначена, а зміни обмежені конкретними файлами й acceptance criteria?  
   **Так → Terra + High.**

4. Чи це bounded tests або read-only exploration одного subsystem без зміни контракту?  
   **Так → Terra + Medium.** Підняти до High, якщо є edge cases.

5. Чи робота механічна, повторювана, однозначна та легко перевіряється?  
   **Так → Luna + Medium.**

6. Якщо жоден пункт не підійшов — **Sol + High**, а агент спочатку уточнює scope і ризики.

## 6. Готові пресети за роллю агента

| Роль | Модель | Reasoning | Типова відповідальність |
|---|---|---|---|
| Архітектор / root | `gpt-5.6-sol` | `xhigh` | декомпозиція, shared contracts, хвилі, інтеграційні рішення |
| Critical reviewer | `gpt-5.6-sol` | `high` або `xhigh` | correctness, race, lifecycle, regressions, test gaps |
| Implementation owner | `gpt-5.6-terra` | `high` | локальна реалізація за затвердженим контрактом |
| Browser / DOM diagnostician | `gpt-5.6-terra` | `high` | відтворення, DevTools-факти, точна локалізація причини |
| Code explorer | `gpt-5.6-terra` | `medium` | read-only карта symbols, call paths, файлів і залежностей |
| Test designer | `gpt-5.6-terra` | `high` | сценарії, edge cases, negative tests одного subsystem |
| Test inventory / fixtures worker | `gpt-5.6-luna` | `medium` | механічне покриття матриці та fixtures |
| Documentation worker | `gpt-5.6-luna` | `medium` | оформлення вже ухвалених рішень |

## 7. Приклади для YouTube-модуля

| Задача | Рекомендована конфігурація | Чому |
|---|---|---|
| Єдиний ownership listeners, observers і timers | Sol + Extra High | наскрізний lifecycle і ризик дублювання |
| Стабільний `start → stop → start` | Sol + Extra High | повторна ініціалізація та cleanup |
| Identity коментаря, deduplication і migration | Sol + Extra High | довготривала цілісність даних |
| Storage atomicity між кількома вкладками | Sol + Extra High | concurrency і lost updates |
| Зміна shared `CommentService` API | Sol + High | великий fan-in і ризик регресій |
| Реалізація вже визначеного adapter method | Terra + High | контракт відомий, scope локальний |
| Selector fix після підтвердження через DevTools | Terra + High | локальна DOM-інтеграція з фактичними даними |
| Unit tests одного стабільного сервісу | Terra + Medium або High | залежить від кількості edge cases |
| Inventory тестів і заповнення fixtures | Luna + Medium | повторювана та перевірювана робота |
| Фінальне рев'ю всіх хвиль | Sol + Extra High | перевірка взаємодії змін |

Для UI/DOM-проблем YouTube Studio модель не повинна вигадувати структуру Polymer або `<iron-list>`. Спочатку потрібні DevTools-факти відповідно до `AGENTS.md`, і лише після цього дозволена реалізація.

## 8. Правила паралельної роботи

### Безпечна схема

У поточному середовищі використовувати root + максимум **3 субагенти** одночасно.

Паралельно добре виконувати:

- read-only exploration різних subsystem;
- незалежний аналіз тестових прогалин;
- review, triage і документацію;
- реалізації з гарантовано неперетинним ownership файлів і контрактів.

Не запускати паралельно:

- двох агентів, які редагують один файл;
- зміни producer і consumer shared API без спочатку зафіксованого контракту;
- дві реалізації, що змінюють один storage key, event type або state owner;
- фінальне рев'ю до завершення залежних write-задач;
- широкі рефактори без чітких file boundaries.

### Рекомендовані хвилі

1. **Хвиля 0 — факти:** read-only exploration, DevTools-діагностика, test inventory.
2. **Хвиля 1 — контракти:** root або Sol-архітектор фіксує API, ownership і acceptance criteria.
3. **Хвиля 2 — реалізація:** Terra-агенти паралельно працюють лише над неперетинними файлами.
4. **Хвиля 3 — складні інтеграції:** Sol закриває lifecycle, races, identity та migration.
5. **Хвиля 4 — верифікація:** тести, build, lint і Sol-review наскрізної поведінки.

Кількість субагентів визначається кількістю **незалежних** задач, а не доступною кількістю слотів. Якщо незалежна задача одна — потрібен один агент.

## 9. Обов'язковий формат задачі для субагента

Кожна task card повинна містити:

```text
ID і назва:
Мета:
Модель:
Reasoning:
Режим: read-only або workspace-write
Owned files:
Заборонені файли:
Залежності від інших задач:
Відомі факти / DevTools evidence:
Acceptance criteria:
Команди перевірки:
Що повернути root-агенту:
```

Мінімальний приклад:

```text
YT-C1 — стабілізувати lifecycle YouTube Studio.
Модель: gpt-5.6-sol.
Reasoning: xhigh.
Режим: workspace-write.
Owned files: [точний список].
Заборонено: змінювати storage schema і unrelated modules.
Залежності: YT-00 завершена, lifecycle contract затверджений.
Acceptance: повторний start/stop не множить listeners, observers і timers.
Перевірка: targeted tests, npm run test, npm run build.
Повернути: змінені файли, докази перевірки, ризики, незакриті питання.
```

## 10. Правила самовибору для агентів

Агент зобов'язаний діяти в такому порядку:

1. Якщо task card уже задає модель і reasoning — використовувати їх.
2. Якщо налаштування не задані — класифікувати задачу за розділом 5.
3. Якщо в процесі виявлено concurrency, lifecycle, shared contract або невідому міграцію — зупинити write-частину і повідомити root про потребу підвищити задачу до Sol.
4. Не розширювати ownership файлів самостійно.
5. Не компенсувати відсутні факти вищим reasoning.
6. Якщо задача стала механічною після затвердження контракту, її можна передати Terra або Luna.

## 11. Ознаки, що модель треба підвищити

Підвищити Luna → Terra або Terra → Sol, якщо з'явилося хоча б одне:

- зміни зачіпають три чи більше модулів;
- існує більше одного власника стану;
- є listeners, observers, timers або повторна ініціалізація;
- проблема проявляється лише на великій кількості коментарів;
- треба мігрувати старі збережені дані;
- тести проходять, але реальний UI нестабільний;
- змінюється shared type, event, storage schema або public service method;
- вимоги суперечливі або acceptance criteria нечіткі.

## 12. Ознаки, що можна використати простішу модель

Знизити Sol → Terra або Terra → Luna можна, якщо одночасно виконуються всі умови:

- контракт уже затверджений;
- точний список файлів відомий;
- немає concurrency і lifecycle;
- зміна не впливає на shared API чи storage schema;
- результат перевіряється однією чіткою командою або тестом;
- помилка легко локалізується і відкатується.

## 13. Optional default для Codex

Якщо потрібні глобальні значення для субагентів, практичний project default:

```toml
[agents]
max_concurrent_threads_per_session = 3
default_subagent_model = "gpt-5.6-terra"
default_subagent_reasoning_effort = "high"
```

Це лише default. Task card для архітектури, lifecycle, identity, races і фінального рев'ю повинна явно перевизначати модель на `gpt-5.6-sol`, а reasoning — на `xhigh` за потреби.

## 14. Джерела і межі рекомендації

Офіційна документація OpenAI рекомендує:

- `gpt-5.6` для складної, неоднозначної, багатокрокової роботи;
- `gpt-5.6-terra` для швидших read-heavy та легших паралельних задач;
- `gpt-5.6-luna` для вузьких, чітких, повторюваних задач;
- `medium` як збалансований reasoning, `high` для складної логіки й edge cases, `xhigh/max` для особливо складних задач;
- обережність із паралельними write-heavy workflows через конфлікти та координаційні витрати.

Джерело: [OpenAI Docs — Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Конкретний розподіл Sol/Terra/Luna в цьому документі є **проєктною політикою**, адаптованою до ризиків цього розширення: Manifest V3, YouTube Studio Polymer/`<iron-list>`, SPA lifecycle, shared storage та вимога Single Source of Truth.
